# batch-commit-log

Append only commit log that groups records into durable segments, so a writer publishes a batch atomically and a reader replays exactly the batches that were committed.

## Requirements

Go 1.22 or newer. Standard library only.

## Build

    go build ./...
    go run ./cmd/logctl --dir <path> stat

## Public interface

`log.Open(dir string, opts Options) (*Log, error)` opens the log directory. The committed set is taken from a persistent index sidecar (`index.idx`) when it can be adopted incrementally; if it is missing, truncated, version-mismatched, checksum-bad or contradictory to the segments, Open rebuilds it from the segment files, so the index is pure cache and opening a grown log no longer decodes every segment entry. A half-written tail of the last segment (crash mid-write) is discarded without error and its reserved sequence stays a permanent hole; any other inconsistency is `ErrCorruptSegment`.
- `(*Log).Append(records [][]byte) (Batch, error)` stages an anonymous batch.
- `(*Log).AppendIdempotent(key string, records [][]byte) (Batch, error)` stages a batch under a key that is unique within the log directory. A repeat with the same key and byte-identical records (same length, order and bytes) returns the first batch and its `Seq`, whether it is still staged or already committed, reserving no new sequence and writing nothing twice. A repeat with different records returns `ErrBatchIDConflict`. An empty key, a key containing a NUL byte, invalid UTF-8, or a key longer than 256 bytes returns `ErrInvalidBatchID`. The key is stored inside the batch's segment entry, so dedup survives process restarts and index rebuilds; a torn tail forgets its incomplete key and leaves the reserved sequence a permanent hole, letting the same key start a new batch.
- `Batch.ID() string` returns the idempotency key for a batch from `AppendIdempotent`, or `""` for an anonymous batch; batches handed to `Scan` report the same ID and records the segment stored.
- `(*Log).Commit(batch Batch) (uint64, error)` makes a batch durable and returns its sequence. The segment entry is synced first, then one index sidecar record; with `Sync`, a failed fsync of either returns `ErrSyncFailed`, both files roll back and the batch stays staged for a retry that never duplicates the entry. Committing the batch returned by a post-commit idempotent retry returns `ErrUnknownBatch` (the original batch is already committed).
- `(*Log).CommitGroup(batches []Batch) ([]uint64, error)` commits several staged batches as one atomic write and one fsync: all become durable together, or all stay staged for a retry. Groups may mix anonymous and keyed batches; each batch keeps its reserved sequence, and a crash never leaves half the group visible. A group containing an already committed or aborted batch returns `ErrUnknownBatch` and writes nothing; the other valid batches stay staged.
- `(*Log).Abort(batch Batch) error` abandons a staged batch — anonymous or keyed, empty or not — without committing it. The reserved sequence becomes a permanent hole: `Read` returns `ErrNotCommitted`, `Scan` skips it and no later append reuses it, across restarts and `index.idx` rebuilds (the hole marker is fsynced into the segment and the sidecar regardless of `Options.Sync`). The batch's idempotency key is released: reusing it, with identical or different records, reserves a fresh sequence; every other batch and key is unaffected. A zero `Batch`, a batch of another log or previous open, or an already committed or aborted batch returns `ErrUnknownBatch` and changes nothing; `Commit`/`CommitGroup` reject an aborted batch the same way. A write, close or sync failure returns `ErrAbortFailed` with the batch and its key still staged under the original sequence — retrying the abort or committing instead never duplicates a record. A crash mid-abort is recovered by the ordinary torn-tail rules: the recognizable aborted sequence stays a permanent hole and durable commits are preserved.
- `(*Log).Read(seq uint64) ([][]byte, error)` returns one committed batch, located directly through the persistent segment-level index (adopted from `index.idx` or rebuilt from the segment files on open). A sequence whose segment was reclaimed by `DeleteThrough` returns `ErrTruncated`, distinct from `ErrUnknownBatch`.
- `(*Log).Scan(from uint64, fn func(Batch) error) error` replays committed batches in order. When `from` falls inside a prefix reclaimed by `DeleteThrough`, the replay starts at the first retained batch; with no retained batches it returns without a callback.
- `(*Log).Segments() []Segment` lists retained segments with their first and last sequence.
- `(*Log).DeleteThrough(seq uint64) (int, error)` reclaims consumed history with a prefix truncation that deletes whole segment files only and returns the number removed. `seq` must be a committed batch; `0` is a no-op returning `0`. Every complete segment whose highest reservation (last committed batch or last hole marker) is at or below `seq` is removed; batches, groups and segments are never split or rewritten, so `seq` in the middle of a segment deletes one segment fewer. An unknown sequence, a hole, a still-staged batch, or a staged/hole reservation at or below `seq` returns `ErrInvalidRetention` and deletes nothing; a write or sync failure returns `ErrRetentionFailed` and leaves the log readable in either its full old or full new state. The truncation point is journaled atomically in `truncate.idx` before any segment is removed, so a crash is completed on reopen and historical sequences still read as `ErrTruncated` even after `index.idx` is rebuilt. Idempotency keys in removed segments are released and may be reused; keys in retained segments keep their dedup/conflict semantics. Segment numbers are never reused.
- `(*Log).AckConsumer(name string, seq uint64) error` persists consumer `name`'s confirmation that the committed prefix through `seq` has been processed, leaving any previously saved replay state untouched; a first registration starts with empty state. A name is registered only with `AckConsumer(name, 0)`; the initial confirmed sequence is zero. Checkpoints only move forward: repeating the current value succeeds without writing, while a smaller value returns `ErrInvalidAck`. A greater target must name a committed batch (a permanent hole may be skipped over, a whole group may be confirmed by its highest member), must not have been reclaimed by `DeleteThrough`, and no still-staged batch with a smaller sequence may sit below it — otherwise `ErrInvalidAck`, and nothing changes. A syntactically invalid name (same rule as idempotency keys; the two namespaces are independent) returns `ErrInvalidConsumer`, and a legal but unregistered name returns `ErrUnknownConsumer`. A successful advance is durable regardless of `Options.Sync`: the target and all earlier committed data are fsynced first, then `consumers.idx` is atomically replaced and synced. A data or metadata sync failure returns `ErrCheckpointFailed` with every consumer still at its previous value, and the call is retryable.
- `(*Log).AckConsumerState(name string, seq uint64, state []byte) error` works like `AckConsumer` but publishes the sequence together with an opaque replay-state blob (at most 1048576 bytes; an oversized blob returns `ErrInvalidCheckpointState`; nil and empty are equivalent; the log keeps its own copy). A new name is registered only at `seq == 0`, and the registration is saved together with the given state; a non-zero seq for an unregistered name is `ErrUnknownConsumer`. Repeating the stored sequence with the identical state succeeds without writing; repeating it with different state returns `ErrCheckpointConflict` and writes nothing. All progress errors of `AckConsumer` apply, checked after the name and the state-size limit. A legal advance fsyncs the target and all earlier committed data first (even when `Options.Sync` is false) and then atomically replaces `consumers.idx`, so the new sequence and state become durable together; a write, close or sync failure is `ErrCheckpointFailed`, every consumer keeps its old value, and a crash during the update restores either the complete old or the complete new table.
- `(*Log).ConsumerSeq(name string) (uint64, error)` returns the confirmed sequence (`0` for a freshly registered consumer); `ErrInvalidConsumer` for a bad name, `ErrUnknownConsumer` for a legal name that has never registered. Consumers replay with `Scan(ConsumerSeq(name)+1, …)` and call `AckConsumer` when the prefix is handled.
- `(*Log).ConsumerCheckpoint(name string) (seq uint64, state []byte, err error)` returns the confirmed sequence together with the opaque state saved by `AckConsumerState`; the returned sequence always agrees with `ConsumerSeq`, and consumers registered through `AckConsumer` (or carried by an old-format `consumers.idx`) read back empty state. The returned slice is an independent copy, the call only reads and never rewrites the file, and it shares `ConsumerSeq`'s name errors.
- `(*Log).DropConsumer(name string) error` durably removes a registration — sequence and replay state — and releases the prefix protection it held (`ErrInvalidConsumer` / `ErrUnknownConsumer` as above; a persistence failure returns `ErrCheckpointFailed`). A reopen never revives a dropped consumer; `AckConsumer(name, 0)` or `AckConsumerState(name, 0, state)` registers it again from zero with empty/fresh state.
- Checkpoint metadata lives in `consumers.idx` in the log directory, independent of the rebuildable `index.idx`: values survive reopens and the deletion or rebuild of `index.idx`, and a directory written before consumers existed (no file) simply has none. Version 2 images carry each consumer's state blob; old version 1 images stay readable with empty state and are only rewritten on the next actual checkpoint change. The whole table is replaced atomically, so a crash recovers either the complete old or the complete new table; a truncated, checksum-bad, wrongly framed, unsupported-version, structurally invalid (including an oversized state blob) or semantically impossible image makes `Open` return `ErrCorruptCheckpoint` — progress is never reset silently.
- `DeleteThrough` keeps its original validation and whole-segment boundaries. When a reclaimable prefix exists, it is deleted only if every registered consumer has confirmed past the highest committed batch in the prefix; otherwise the call returns `ErrRetentionBlocked` and changes no file, index entry or idempotency key. Hole-only segments carry no data and do not count toward protection. With no consumers the original behavior is unchanged.
- `type Options struct { SegmentBytes int; Sync bool }`.
- `log.ErrNotCommitted`, `log.ErrCorruptSegment`, `log.ErrUnknownBatch`, `log.ErrInvalidOptions`, `log.ErrSyncFailed`, `log.ErrInvalidBatchID`, `log.ErrBatchIDConflict`, `log.ErrTruncated`, `log.ErrInvalidRetention`, `log.ErrRetentionFailed`, `log.ErrInvalidConsumer`, `log.ErrUnknownConsumer`, `log.ErrInvalidAck`, `log.ErrInvalidCheckpointState`, `log.ErrCheckpointConflict`, `log.ErrCheckpointFailed`, `log.ErrCorruptCheckpoint`, `log.ErrRetentionBlocked`, `log.ErrAbortFailed` error values.

## Limits

Single writer; concurrent appends are not serialised.
Records are opaque bytes.
Prefix truncation reclaims whole segment files only; there is no entry-level compaction and no replication.
